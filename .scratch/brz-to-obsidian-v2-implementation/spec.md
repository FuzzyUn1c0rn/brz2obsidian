# BRZ to Obsidian — version 2 implementation specification

Status: ready-for-agent

Testing-boundary confirmation: accepted by the user on 2026-10-04

## Problem Statement

The user wants to convert the Software Engineering Brain into an ordinary, editable Obsidian vault. The current converter handles the feature classes in two earlier exports, but refuses this archive's thought types and assignments, one differently marked active thought note, and four zero-length declarations for absent TXT payloads. Video metadata is retained without the requested native presentation. Retaining these facts only in a migration record would not provide useful category navigation or a consistent way to create and maintain objects after migration.

All three archives come from the same TheBrain version and exercise complementary features. Version 2 must extend coverage cumulatively, preserve the earlier capabilities, and deliver the actual complete conversion. The disposable prototype established presentation and editing behavior; it did not establish full conversion or final acceptance.

## Solution

Extend the existing local library and CLI to convert the complete reviewed archive into a fresh vault. Map thought types faithfully to linked category notes, materialize every typed member, and provide native templates, properties, contextual Bases and category dashboards following the inspected kepano reference pattern. Preserve Markdown, resources, identities, graph relationships, source tags and original evidence through the existing verified publication workflow.

Keep Icon first and Note second in member tables. Omit the decorative Appearance display and the unused foreground/background colour properties. Icons inherit dynamically from an explicitly chosen category, with optional member overrides; source colours remain preserved in the migration record only. Category notes show Members/Gallery Bases immediately after their title, without a generated introductory icon image; preserve their source content/resources below the Bases. Keep category icon properties/assets for dashboard images and separately editable body-icon snapshots on ordinary/member notes. Preserve PDFs and exact video URLs, add the reviewed native video presentation, and report approved absent TXT records honestly.

Provide a concise human/agent guide, reusable future-category starters and a read-only convention checker. Complete independent preservation checks for all three archives and native review of actual converter outputs before claiming a finished v2.

## Implementation Decisions

1. **Cumulative release boundary.** Extend the reviewed exchange-format-5 profile for the feature classes established by the three archives and controlled evidence. They are acceptance cases, not a fingerprint allowlist or three application-version targets. Preserve earlier feature behavior except for the explicitly accepted v2 additions to note properties, icons, dashboards and support artifacts.
2. **Architecture.** Retain the accepted source-neutral core and inward Pydantic contracts. The TheBrain adapter owns numeric source roles, assignment joins, timestamp interpretation, resource eligibility and anomaly recognition. Pure analysis/planning owns consistency, selections, naming and destination obligations. The Obsidian renderer owns Markdown, frontmatter, Bases, templates and native configuration. The publisher owns verified filesystem publication. The application workflow orchestrates injected interfaces; the CLI remains thin.
3. **Shared facts and versions.** Extend strict, closed, frozen contracts with immutable classification assignments, definition roles, declared appearance, calendar-date facts and reviewed video-presentation facts. Generic identities remain opaque. Source-specific evidence remains outside interpretation in the core. Version extended snapshot/policy contracts, renderer, source profile and serialized migration/result schemas explicitly as version 2; retain their established schema identities and existing result fields. Document the schema change rather than silently presenting extended closed shapes as version 1. The BRZ format remains 5. Update the test-only alternate adapter to the current contract with empty optional new facts where appropriate.
4. **Public conversion behavior.** Retain public inspect/convert workflow signatures, dependency injection, default wiring, text/JSON modes, console/module entry points and existing command arguments. Retain clean/warnings/refused/failed outcomes and exit codes 0/2/1/1. Inspection remains read-only, measures only available counts and has no publication receipt. Conversion prepares afresh; actual counts and a durable receipt require verified publication. Document the version-2 envelope for consumers and preserve explicit failure phase/evidence/guidance.
5. **Type identity and membership.** Recognize the evidenced type thought role and type-to-ordinary instance relationship. Require every populated ordinary thought TypeId to identify one live type and agree exactly with its exported instance relationship; also reject instance links without the corresponding assignment, duplicates, conflicting assignments, invalid endpoint roles and dangling definitions. Keep type assignment separate from ordinary hierarchy, jump and source-tag membership. Supertype inheritance and custom link types remain unsupported.
6. **Materialization.** Create a note for every supported type definition and every assigned ordinary member, even without authored content or ordinary resources. Start the existing content/Home/hierarchy selection policy from those required notes; retain its greedy, canonically tied hierarchy cover for remaining untyped empty items. Classification alone must not materialize unrelated untyped thoughts. Definition and member notes retain source identity, original titles, labels, content/resources and relevant ordinary relationships. Retain system-to-type connections as evidence without adding visible hierarchy.
7. **Faithful category mapping.** Map each real thought type directly to one category dashboard using its actual source name and deterministic collision-safe assignment. Import one linked membership and appearance provider for each typed member. Do not infer categories from prose, rename them to reference plural forms, fabricate domain-specific properties, or inherit definition content/resources into members. Future manual memberships may be multiple.
8. **Operational organization.** Keep the existing root Home and the Notes/Attachments operational areas; add Categories and Templates at the vault root, with Bases beneath Templates. Preserve original Home content and entry behavior, adding a discoverable Categories overview. Folder placement is not member classification. Use the existing canonical naming/sanitation/truncation/collision rules across imported targets and support artifacts. Reserve overview, guide, starter, template, Base and configuration artifacts before assigning imported paths; preserve intentional uncreated-target reservations and the existing conservative Windows path limits.
9. **Canonical properties.** Use the vocabulary and cardinalities in the table below. Serialize native linked values safely as quoted wikilinks, date values as calendar dates and native lists as lists. Do not mine note prose for schema values. Imported source identity is excluded from new-note templates and starters; custom future vocabulary is allowed when intentionally documented.

   | Property | Contract |
   | --- | --- |
   | `categories` | List of links to category notes; an untyped note may have an empty list. |
   | `appearance_category` | Optional single link to a category also present in memberships; empty means no inherited dashboard icon. |
   | `icon` | Optional link to one preserved local image; category default or explicit member override. |
   | `created`, `updated` | Optional valid calendar dates with the source/new-note meanings below. |
   | `tags`, `aliases` | Native lists; source tags retain their separate adaptation. No automatic alias invention. |
   | `source_collection_id`, `source_item_id` | Paired opaque imported identities, stable through renames; absent on genuinely new objects. |

10. **Dates and provenance.** Imported created/updated use the encoded calendar component of source thought creation/overall modification respectively, without timezone conversion or a text-only modification claim. Missing values remain empty; populated values must support a valid calendar date without inventing a fallback. Preserve exact full original strings, other timestamps and omission/null distinctions. Migration time remains separate run provenance. New templates initialize both dates to the insertion day's ISO calendar date using native variables; subsequent updated changes are explicit.
11. **Dynamic icon semantics.** Determine a member's explicit owned icon independently from its category's default. A valid explicit icon wins; otherwise use the valid appearance category's current icon. An empty provider is a valid opt-out. A populated provider must resolve to a real category in memberships; invalid/dangling/nonmember providers provide no inherited icon, are visibly distinguishable in member views and are reported by the checker. Do not silently reselect providers after membership changes. An explicit valid icon remains available with a blank or invalid provider. Defaults are not copied into override properties.
12. **Icon preservation and snapshots.** Copy source icon payloads once through existing ownership/naming rules and link to those files wherever used. Generate initial note-body icon references from the migration-time effective icon for created ordinary/member items where an image is available. These are editable snapshots and are not rewritten by later category/provider property changes; editing the shared image bytes may naturally affect references. Category dashboards omit this generated body-image reference and show Members/Gallery immediately after the title, before retained source labels, authored content/images, resources and relationships. Their icon properties, assets and neutral effective-icon decisions remain available for dynamic Base images; adaptation evidence must not claim an absent category body snapshot. Do not create a note solely for an untyped decorative icon. Preserve opaque icon tokens without interpreting them as universal inheritance markers.
13. **Colours and labels.** Preserve declared source colours and their raw encoding in the migration record, including source-neutral DeclaredAppearance facts and original numeric evidence. Normalize only the opaque ARGB cases established by evidence; do not invent alpha/color-encoding behavior for unreviewed forms. Do not emit `foreground_color` or `background_color` in note frontmatter, templates, starters, native property typing, Bases or other vault presentation. These names are outside the canonical vocabulary; the checker permits manually added properties with these names as ordinary custom extensions. Preserve each item's own label without synthesizing a member label from its type label. The coloured duplicate note-name Appearance display and its decorative rendering are omitted from all generated member views.
14. **Native categories and discovery.** Category dashboards use the reference's native categories tag convention, with the agreed operational folder guard for category-role discovery. Member queries use linked membership, not prose, hierarchy, appearance-provider links or source tag names. Exclude template/attachment support areas deliberately; do not use a filename-substring exclusion that hides legitimate notes containing Template. The overview requires the proper category role and excludes an ordinary source tag or same-basename ordinary note.
15. **Contextual member Bases.** Embed native member queries in each category dashboard using the embedding category's identity. Preserve that membership discovery through native link-preserving renames; do not write the old category's title into the member predicate. Offer the demonstrated Members table and Gallery presentation. Member tables start Icon, Note, then Inheritance, categories, created, updated, retaining the reviewed ordering after the removed Appearance column. Sort members deterministically by note name. The overview starts Icon then Category and does not expose source colour fields. Native cards use the effective icon. Standalone contextual Bases lack an embedding category; document category dashboards as the supported entry point without inventing a default category.
16. **Reference mechanism and deliberate adaptations.** Follow actual manual template selection, linked category properties, independent Base queries and category-note body embeds. Introduce no template/base/vault_role registry properties, automatic category-to-template binding or required community plugin. Adapt the reference through faithful source names, complete member materialization, explicit icon providers, robust exclusions, qualified collision-safe links and contextual rename-safe member views. Preserve the distinction between a useful reference pattern and exact cloning.
17. **Template delivery.** Generate one generic new-note template and one complete template per imported category, sharing the canonical core and initializing that category's membership/provider. Leave optional overrides blank so defaults remain live. Templates initialize structure; they do not enforce continuing schemas. Deliver category-note, member-template and Base starter examples plus a short extension recipe. Starters create no imported IDs, unreviewed semantic fields or fabricated relationships.
18. **Existing-note workflow.** Use full templates on new notes. Edit the categories property directly on existing notes, preserving established dates, content, identity and provider. Do not deliver additional category-only templates. Explain the observed native scalar overwrite behavior and explicitly maintained update dates; do not promise the core Templates plugin protects arbitrary reinsertion. A membership edit that invalidates the provider is handled by the existing invalid-provider convention.
19. **Native configuration.** Enable the bundled Templates and Bases plugins, configure native template discovery/date insertion and property types, retain established Home/bookmark/opening preferences and link-preserving rename settings, and include all generated configuration in the verified manifest and migration record. Configure only required native capabilities; do not copy unrelated reference toggles, global settings, CSS or plugins. No community plugin is required.
20. **Unusual active note.** Support a sole, unambiguous, present thought-owned Type-1/NoteType-0 canonical Notes.md payload on an ordinary owner as active content when valid decoded Markdown is nonempty and there is no competing thought-note candidate. Require normal state, length, CRC, ownership and supported-reference checks. Retain exact original bytes and source-marker evidence. Keep existing empty-placeholder handling. Do not treat every Markdown attachment as active thought-note content or claim its numeric marker records UI selection.
21. **Approved zero-length TXT finding.** Add recognition rule `thebrain-format5/zero-length-absent-txt/v1` for the evidenced case: thought-owned Type 15/NoteType 0, valid TXT location, declared length exactly zero, attachment state 2, absent corresponding bytes, filename stem identifying one PDF attachment under the same owner, and that PDF present with its ordinary state/role, CRC-valid bytes and matching declared length. Require all normal identity, ownership and role checks. Emit a source finding with the TXT/PDF association and integrity evidence; generic analysis permits only the reviewed profile's warning disposition with issue code `approved_source_gap`. A mismatched stem/owner/state/length, ambiguous association or absent/corrupt PDF refuses rather than widening the exception.
22. **Existing warnings and reporting.** Preserve the earlier positive-length absent-TXT rule and exact intact-icon length-discrepancy exception. Each missing TXT declaration remains a successful-with-warnings finding, recorded individually with retained metadata and a brief source-filename notice on an existing owner note. Create no fake TXT bytes, usable local link or note solely for that gap. Do not call the absent TXT optional, a cache, proven extraction failure or evidence of restored-source search. Document PDF vault Search and remote-video limits once in the human report/guide, separately from per-record source gaps.
23. **PDFs and other resources.** Preserve intact PDF and generic resource bytes through existing copy/accounting contracts. Retain source URLs and external directory references without fetching them during conversion. Native PDF opening is required, but extraction, indexing and equivalent TheBrain PDF body search are outside scope. Keep inline images inline and prevent decorative icons from cluttering Resources.
24. **Video adaptation.** Preserve exact source URL spelling and query parameters and retain VideoHtml as source evidence. For the reviewed YouTube resource forms, generate a native embed from the usable URL/validated provider facts alongside that original link; never execute or copy arbitrary archived iframe HTML into the vault. Preserve the evidenced timing intent through native embedding, including the demonstrated 18-second start. Account for any derived embed URL separately from the preserved resource URL. Remote availability is a destination limitation, not a missing-payload finding. Unreviewed video semantics cannot be silently admitted as playable content.
25. **Authored Markdown and evidence.** Continue adapting only supported bound source-local reference spans. Preserve everything else, including fenced/inline code, blockquotes and original newline spelling; generated frontmatter/navigation/icon/notice additions are explicitly separated and accounted for. Keep exact original note backups, every original JSON record/field/value/history entry, raw dates, omission/null distinctions and opaque display/settings data. Unknown metadata does not authorize an unsupported semantic feature.
26. **Refusal and source accounting.** Continue refusing unsafe/corrupt ZIPs, ambiguous members/identities, live/deleted overlap, invalid ownership, conflicting assignments/content, missing required payloads, unresolved required references and unaccounted physical bytes. Retain reviewed Home and ordinary relationship signatures; system-to-type retention is the narrow new endpoint allowance. Nonempty unreviewed event/access/custom-field features, type hierarchy and custom link types remain refused. No caller warning allowlist can bypass coverage.
27. **Manifest, accounting and reproducibility.** Bind all normalization/planning/rendering obligations to source identity and digest. Include classification assignments, category/member targets, declared versus inherited icon decisions, date provenance, generated templates/Bases/configuration, original backups and per-record finding evidence in the versioned migration record. Every actual file has a verified manifest entry; intentional uncreated targets are reserved without pretending they exist. Existing note counts include created imported items, including definitions, while generated overview/template/guide/Base support files remain separately accounted. Add explicit classification/support counts without substituting counts for evidence. Repeat/reordered inputs retain logical selection, paths, content and presentation subject to established source-evidence order/fingerprint and run-metadata differences.
28. **Transactional publication.** Retain absent/empty-destination checks, owned staging, streamed payload copying, source consistency checks, complete hash/length/manifest verification, atomic commit/race protections and owned cleanup. Preserve a successful receipt after later teardown failure and report that publication occurred. Never overwrite caller-owned files, merge into an edited vault, or treat an inspected plan as verified publication.
29. **Read-only checker interface.** Add a source-independent public check_vault operation and thin check-vault CLI command accepting a vault and optional JSON output. Return durable strict results with schema `brz2obsidian.vault-check`, schema_version 1, outcome clean/issues/failed, vault identity/location, measured counts, checked scope and ordered issues. Clean checks exit 0; found convention problems exit 2; operational failure/invalid invocation exits 1. Each diagnostic includes code, artifact relative to the vault when available, optional property/reference, message, guidance and any ambiguous candidate targets. Use stable codes for invalid frontmatter/property/category/provider, missing Base/image, ambiguous reference, duplicate source identity, unsafe reference and read failure. Measurements unavailable after failure remain null. The checker needs neither the BRZ archive nor GUI access and never repairs, renames, creates files or rewrites notes.
30. **Checker coverage.** Validate known property cardinalities/types, valid category roles, provider membership/resolution, required Base/local-image targets, imported identity pairs and duplicate source-identity pairs. Read YAML as data, report malformed or duplicate-key frontmatter and continue other readable notes without executing YAML objects. Accept unrelated custom properties and intentional uncreated ordinary targets. Treat native date variables as template syntax in template scope, rather than invalid authored dates. Resolve qualified references deterministically; accept shortened references only when one target is unambiguous, and report ambiguous category/provider/media references without choosing a convenient file. Do not require links to retain their generated spelling, fabricate source IDs, or infer semantic relationships from prose.
31. **Checker containment and limits.** Read only the supplied vault and references contained within it; report unsafe required references without following them outside the vault. Evaluate actual notes/properties/Bases rather than trusting the migration record as current mutable state. Explain its bounded scope: structural conventions, not schema enforcement, all-purpose broken-link checking, source-preservation proof or continuing date maintenance. Keep it separate from strict migration validation and the independent acceptance audit.
32. **Delivery and environment.** Use the project virtual environment for Python development, dependency installation, packaging and tooling. Introduce only needed packages and keep runtime/build/development manifests reproducible. Keep private inputs, outputs and native evidence local and ignored; public fixtures are synthetic and public reports contain aggregate/structural evidence. Deliver updated installation/library/CLI/schema/checker/reference-adaptation guidance and a source-feature comparison. Specification publication and ticket creation are milestones; complete implementation and actual converted-vault acceptance finish the map.

## Out of Scope

- Synchronization, merging into an edited vault, overwriting a nonempty destination or editing source archives/Brains.
- Recreating TheBrain's Plex, full type inheritance, inherited note contents, subtype hierarchies, custom link types, custom fields or other unexamined semantic features.
- Required community plugins, Maps, custom registries, automatic template selection, global inherited UI styling or decorative Appearance rendering.
- PDF extraction/indexing or equivalent TheBrain PDF body search; video downloads, universal providers, executing archived HTML or guaranteeing remote/offline playback.
- Additive category-only production templates, automatic update dates, body-icon propagation, automated object creation/rename/repair, schema enforcement, an agent platform or deduplication by title.
- Support for additional source formats or unverified application/platform versions; the alternate adapter remains a test-only substitution proof.
- Remote publication of private evidence, implementation or specification; publication here means the local Markdown issue tracker.
