## Question

Which category templates, canonical properties and human/agent maintenance conventions should version 2 deliver with the converted vault, and does that include executable maintenance tooling?

Use the inspected kepano reference and the agreed category representation. Choose the template associated with each supported category and the meanings/cardinality of common or domain-specific properties, without inventing values from note prose or treating source tags/hierarchy as semantic object fields. Distinguish existing imported data, blank fields offered for future authoring, and defaults used when creating a new note. Preserve source evidence and authored content.

Decide how a human or agent finds the appropriate template, assigns one or more destination categories, uses linked relationship values, handles identity/name collisions, and extends the vocabulary. Distinguish a template initializing a note from a schema being validated or enforced. Establish whether source timestamps, future note timestamps and migration provenance have separate meanings.

Agree the delivery boundary: generated templates/Bases and a concise convention guide; mechanical validation/creation helpers if explicitly required; or a broader ongoing maintenance workflow. The existing effort is a one-time fresh-vault migration. Do not silently convert that into a synchronization system, agent platform or schema-enforcement service. Add focused research/implementation prerequisites if the human expands scope.

The user explicitly requires usable native Obsidian templates. Deliver the bundled Templates core plugin enabled and its template-folder setting configured for the generated vault, and verify actual template insertion in the disposable native trial. The accepted maintenance-tooling boundary is recorded in the Answer.

Record only decisions reached through live exchange. Keep actual source-specific template examples and trial vaults private. Update domain terms as meanings crystallize; detailed schemas and testing seams ultimately belong in the required to-spec artifact.

## Accepted design tree

- **Q1/Q10 maintenance:** Deliver editable templates/Bases, a concise human/agent convention guide and a bounded read-only convention checker. Check known structural conventions, allow intentional extensions and uncreated ordinary targets, and keep migration-integrity validation separate. No creation/rename/repair automation is included.
- **Q2/Q5 template depth and vocabulary:** Deliver one generic note template and complete templates for each of the seven actual categories, sharing the canonical category/appearance/date/tag/alias core recorded below. Add semantic fields only through explicit design, without inferring fields or values from type names/prose.
- **Q3/Q9 time:** Imported creation/modification dates use the source thought's encoded calendar component as `YYYY-MM-DD`, with exact full strings retained in provenance and migration time separate. New notes initialize both dates at insertion; subsequent updates are maintained explicitly. No timezone or text-only modification meaning is inferred.
- **Q4/Q8 layout and identity:** Retain root Home, Notes and Attachments; add Categories, Templates and Templates/Bases. Folder placement does not determine category membership. Preserve imported identity and deterministic collision naming through renames; future objects receive no fabricated source IDs.
- **Q7/Q11 appearance:** A populated appearance provider must be an existing category in memberships; invalid providers are reported without reselection/repair. An empty provider is a valid opt-out. Per-field explicit overrides and separately editable note-icon snapshots retain their accepted behavior.
- **Q6/Q12 reference mechanism and extension:** Use native template selection, linked memberships, independent Base queries and category-note body embeds, with the reference's `categories` tag identifying dashboards by convention and deliberate operational/collision guards. Deliver a walkthrough and reusable category/template/Base starter examples. The proposed `template`, `base` and `vault_role` registry fields are withdrawn.
- **Verification handoff:** Template insertion/composition, merging, membership discovery and renames remain native-trial checks. Exact paths, reservations, query expressions, serialization and checker command/result/testing contracts belong in the required to-spec artifact after the trial.

## Answer

The user accepted Q1-Q12 through the live exchange, including the corrected Q6 mechanism established by the [actual reference-vault recheck](../research/kepano-template-base-mechanism.md). Version 2 delivers usable native templates, category dashboards/Bases, a concise human/agent convention guide, reusable extension examples and a bounded read-only convention checker.

### Native workflow and operational layout

Keep root Home, `Notes/` and `Attachments/`; add `Categories/`, `Templates/` and `Templates/Bases/`. Classification comes from metadata and links, independently of folder placement. Preserve the existing deterministic imported naming/collision guarantees; reserve new support artifacts and qualify links where needed. Exact reservations and generated names belong in the specification.

Enable the bundled Templates and Bases core plugins and configure the Templates folder. Follow kepano's actual workflow: a human selects a native template; insertion initializes linked `categories`; a separate Base queries memberships; the category note embeds its Base in the body. Category dashboards use native `tags: [categories]` by convention, with deliberate operational/collision guards so ordinary source tags or prose links cannot identify dashboards accidentally. Do not implement the withdrawn `template`, `base` or `vault_role` registry properties. Changing memberships updates query input without selecting or reapplying a template.

Deliver one generic note template plus complete templates for each of the seven actual categories. Templates are reusable initial structures, not ongoing enforcement. Each category template uses the agreed common core and its linked category membership; do not infer domain-specific fields or values from a type name or prose. Additional semantic fields require an explicit meaning and documented extension. The guide explains template selection and composition, safe insertion into existing notes, lookup before creating an entity and link-preserving renames. Native merging must be tested for preservation of authored content, established creation dates and imported identity.

### Canonical properties and appearance

The later [native maintenance agreement](12-native-maintenance-adaptations.md) refines the workflow: full templates are for new notes; existing-note memberships are edited directly, without delivering additive templates. Category-member Bases use contextual queries entered through dashboards so category renames preserve discovery. The checker accepts unambiguously resolved shortened links. The prototype review also removed the decorative Appearance display; dynamic icons remain required and source colour facts remain metadata.

| Property | Meaning and cardinality |
| --- | --- |
| `categories` | List of linked category notes; future notes may have multiple memberships. |
| `appearance_category` | Optional single linked category chosen from memberships to supply default appearance, independently of membership order. |
| `icon` | Optional linked local image: a category default or an explicit member override. |
| `foreground_color`, `background_color` | Optional colour values: category defaults or explicit member overrides. |
| `created`, `updated` | Calendar dates with the meanings below; unavailable imported values remain empty. |
| `tags`, `aliases` | Optional native lists; source-tag adaptation remains separate from category membership. No automatic alias invention is required. |
| `source_collection_id`, `source_item_id` | Imported-only source identity, excluded from templates and future object examples. |

Bases derive inherited appearance rather than copying defaults into member override properties. Each explicit member value takes precedence over its corresponding default. A populated provider must resolve to an existing category also present in memberships; a deleted, dangling or nonmember provider is reported and supplies no inherited values. Do not silently select another category or repair the note. An intentionally empty provider is valid: membership remains, but no dashboard appearance is inherited. Explicit overrides and normal presentation remain available.

Note-body icons retain the accepted migration-snapshot behavior and remain separately editable. Editing or clearing the provider/category appearance properties does not automatically rewrite or remove those body images. Raw source declarations and inheritance evidence remain preserved in the migration record.

### Dates and identity

Use `YYYY-MM-DD`, matching the reference's date convention. For imported notes, `created` follows source thought creation and `updated` follows overall source thought modification, including its broader item meaning rather than claiming a text-only edit date. Extract the calendar component encoded in the source record without timezone inference/conversion or claiming equivalence to TheBrain's local display. Preserve exact complete original timestamp strings in the migration record and keep migration time separate. Other unfamiliar timestamp fields retain the coverage ticket's uninterpreted treatment.

New-note templates initialize both dates to the authoring date at insertion. Later `updated` changes are maintained explicitly; the Templates plugin supplies no continuing date maintenance. Applying another template must not silently reset existing dates or imported identity.

Imported source identity remains stable through renames. Never merge entities solely by title. Before creating a future object, humans/agents look for an existing name, alias and category using the guide's conventions, then select the appropriate template and link related entities. Future objects receive no fabricated Brain/source IDs.

### Checker and future extension

Deliver a checker that reads and reports known structural convention problems: wrong known-property types, invalid category/appearance references, missing referenced Bases/local image targets and duplicate imported source identities. Allow unrelated custom properties; require documented meanings for intentional vocabulary extensions. Intentional uncreated ordinary note targets are valid and are not generic broken-link errors. Keep the post-migration convention checker separate from strict initial migration preservation/integrity validation. Specify its precise command, result contract and public testing seams through to-spec.

The checker does not repair files, rewrite source-derived content or enforce an ongoing schema. Creation, rename and repair automation, synchronization and an agent platform are outside this accepted delivery boundary.

Provide a short walkthrough and reusable starter examples for a future category note, member template and Base. Use the same native category tag, linked membership, query and body-embed pattern; omit imported IDs from future objects and document any new semantic properties. Reference adaptations are deliberate: preserve source identity/appearance, materialize typed members, use collision-safe qualified links and operational exclusions instead of the reference's broad filename-substring exclusions. Do not copy unrelated reference plugin toggles or require a community plugin.
