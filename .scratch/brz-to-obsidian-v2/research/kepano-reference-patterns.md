Checked: 2026-10-04. Evidence for [Evaluate the kepano reference vault](../issues/10-kepano-reference-patterns.md). Repository pinned to [`473697347a0eaac790a6596229c741b3915f3b77`](https://github.com/kepano/kepano-obsidian/tree/473697347a0eaac790a6596229c741b3915f3b77), authored 2026-01-08. A data-only clone is kept under ignored `brz/reference-research/kepano-obsidian/`; tracked paths, Markdown/frontmatter and Base definitions were inspected without running repository code. No private archive data was uploaded, production vault generated or GUI behavior tested.

**Finding:** the proposed category/template/property/Base/dashboard approach has a concrete reference implementation. Its categories are linked notes that also act as dashboards; templates initialize metadata, and reusable Bases select existing files. It is a convention-based system, rather than evidence of class enforcement. Mapping the supplied thought types into that architecture is viable as a candidate, but source assignment, materialization and appearance rules still require human decisions.

## Actual files versus the explanatory model

The pinned tree contains **21 category notes, 52 Markdown templates, 30 Base files with 75 views**, and example objects in `References`, `Notes` and `Clippings`. Bases are stored under `Templates/Bases`. No Base contains `groupBy`; the tracked tree contains no agent instructions, validator or maintenance scripts. These are exhaustive tree/text observations, not claims about Ango's unpublished personal vault. [Pinned tree](https://github.com/kepano/kepano-obsidian/tree/473697347a0eaac790a6596229c741b3915f3b77).

Ango's [article](https://stephango.com/vault) describes shallow folders, title-named references, plural categories, reused properties and composable templates. It distinguishes the download's `Categories`/`Notes` folders from his personal root-level placement and values unresolved links. His personal maintenance description is manual; it does not supply an agent workflow. From the requested [Obsidian article index](https://stephango.com/topics/obsidian/), [File over app](https://stephango.com/file-over-app) supports durable user-owned files, while [Evergreen notes](https://stephango.com/evergreen-notes) discusses composing ideas. Neither article specifies a typed database schema or authorizes rewriting imported thought titles.

### Categories, secondary taxonomies and appearance are distinct

There are real multiple-category objects: [Obsidian](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/References/Obsidian.md) has Companies and Apps categories; a [recipe example](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/References/Brown%20butter%20nectarine%20tart.md) combines Recipes and Clippings. Categories do not imply one exclusive object class. Also, not every referenced category has its own dashboard: Apps has no category note/Base in this pinned tree.

The separate property `type` is another linked taxonomy. [Fushimi Inari](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/References/Fushimi%20Inari.md) has **one category, Places**, and **two type links, Parks and Shrines**. [Parks](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/References/Parks.md) is a reference note tagged `places/types`, carrying an icon name/color and contextual Places/Map embeds; it has no `categories` property and is not a category dashboard under `Categories`. The linked Shrines note is absent.

[Map.base](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Bases/Map.base) obtains icon/color from the **first `type` link's file properties** and assigns those formulas to map-marker presentation. It does not derive category style precedence or supply member-override fallbacks. [Places](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Categories/Places.md) embeds both Map and Places Bases. Map views require the separately installed official Maps community plugin; this portion therefore exceeds our current core-only baseline. [Native Map documentation](https://obsidian.md/help/bases/views/map).

## Reusable conventions and limits

- **Flat linked metadata:** shared vocabulary includes `categories`, `type`, `topics`, `genre`, `author`, `people`, `loc`, dates and ratings. [.obsidian/types.json](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/.obsidian/types.json) gives property names vault-wide primitive editor types, including list-like categories. That is not a per-category required-field contract. Native Templates insert text and merge properties when invoked; editing a template does not establish continuing enforcement. [Templates](https://obsidian.md/help/plugins/templates), [Properties](https://obsidian.md/help/properties).
- **Reusable queries:** membership filters and named views provide category indexes and contextual object dashboards. Native Bases keeps note fields in Markdown, formulas in the Base, and defines `this` by display context. A calculated appearance is view output rather than a documented mutation of member frontmatter. Core grouping is supported through `groupBy`, even though the reference does not use it; a grouped view is an optional design choice. [Bases syntax](https://obsidian.md/help/bases/syntax).
- **Several presentations:** [Everything.base](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Bases/Everything.base) combines tables and image cards; [Movies.base](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Bases/Movies.base) adds watchlist/favorite/person views with independent filters, sorts and column widths. These patterns do not require reproducing every view for our seven categories.
- **Relationships remain explicit links:** [Backlinks.base](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Bases/Backlinks.base) lists incoming links; [Related.base](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Bases/Related.base) ranks overlap and direct links. Its computed relatedness is not TheBrain's explicit Jump relationship; substituting it would change source meaning.
- **Adapt rather than copy blindly:** Books exposes `length` where its template/object uses `pages`; its Top rated view sorts by `last` without a rating filter. [Product Template](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Product%20Template.md) uses `monthly-uses`, while [Products.base](https://github.com/kepano/kepano-obsidian/blob/473697347a0eaac790a6596229c741b3915f3b77/Templates/Bases/Products.base) uses `monthlyUses`. Some templates use scalar categories where others use lists. These are source-text mismatches; their runtime consequences were not tested. Filename-substring exclusion could also hide a legitimate migrated thought. Prefer an explicitly chosen, consistent generated convention and test it.

The requested [TheBrain 15 page](https://www.thebrain.com/products/thebrain/thebrain15) describes type/tag filters, multiple-parent navigation, Cerebro, scripting and a local API. It supplies no BRZ schema for our proposed domain fields and no reason to add ongoing automation to a one-time migration.

## Comparison with this migration and deliberate choices

Our [inventory](source-differences.md) establishes seven source type definitions and 195 ordinary members with one `TypeId` each; type definitions have no supertype assignments. Source tags and ordinary hierarchy remain separate meanings. The new Brain has no source tags, but the earlier accepted archives do. Source note probes found no YAML frontmatter; Ango's bibliographic/project/place fields cannot be inferred simply from a thought's type.

The [native source controls](native-source-behavior.md) establish field-specific icon/color inheritance with direct overrides. A member-owned icon wins; resetting a direct color restores the type's color. Type labels did **not** appear as generic inherited member labels in the tested v15 cases. Icon tokens also change with attachments, so they cannot be treated as a complete inheritance grammar. Kepano's first-type map formula is a useful display technique, not a replacement for those source rules. Native alternatives and their trial boundaries remain in [Obsidian options](obsidian-type-options.md).

Candidate conventions, requiring decisions rather than automatic adoption:

1. Map each source type to a linked category/dashboard with an initial one-element membership list; alternatively retain source type assignment separately from broader editable destination categories. Additional categories are a destination capability, not permission to classify source content or invent memberships.
2. Create shared/category templates from agreed source-backed metadata and explicit empty fields, then reusable Bases/dashboards. Template default dates must not overwrite source dates. Required fields, domain schemas and category-specific relationships need explicit human definitions; source titles or prose are not authorization to derive them.
3. Choose a materialization policy compatible with dashboard expectations. Bases query actual files, whereas [v1](../../brz-to-obsidian-v1/spec.md) intentionally leaves many empty targets uncreated. A parent-supplied aggregate check on 2026-10-04 found **43 of 195 typed thoughts with substantive note/resource content and 152 without either**; some of those 152 may already be selected hierarchy notes, so this is **not** a count of additional files. Its private evidence is `brz/v2-native-source-ticket/category-design-counts.json`. Full category membership requires either more member notes or a separately specified representation for uncreated members.
4. Add category/template/Base support folders while deciding whether to retain v1's root Home, `Notes` and owner-grouped `Attachments`. Kepano's root/reference distinction and pluralizing convention do not justify reclassifying or renaming imported content. Preserve deterministic collisions, unique reserved targets, exact original titles, identity traceability and present payload bytes from v1 regardless of the chosen presentation.
5. Provide clear textual editing conventions for humans/agents (**candidate benefit:** flat files and consistent vocabulary are easy to inspect). A running validator, classifier, reconciliation script or agent service is separate work requiring scope decisions. Templates and Bases themselves do not constitute that toolkit, and ordinary user edits after migration need not trigger converter activity.

## Focused questions for the next grilling session

- Should categories initially mean exactly the seven source type assignments, or should source type remain a separate field beneath a broader destination classification system?
- Must every typed thought appear as an editable Base row, including empty members, or is preserving some as uncreated targets acceptable with a readable membership fallback?
- Where should source appearance be visible: note content, category cards, Graph colors or another chosen surface? How should member overrides be shown? Is the core-only baseline retained?

Template fields, useful columns/views, support-folder layout and ongoing maintenance scope can be settled in a focused follow-up after these representation choices. None requires copying Ango's personal domain schemas or building a new service by default.

No answers or destination design are accepted here. After those decisions, the disposable trial must check membership completeness, template merging, quoted links/renames, multi-category queries, chosen appearance/override behavior, configuration portability and exclusion of support files; reference file presence is not proof of native rendering.
