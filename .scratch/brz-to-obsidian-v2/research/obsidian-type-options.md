# Obsidian options for thought types and shared appearance

Checked: 2026-10-04. Supports [Establish Obsidian options for types and inherited appearance](../issues/02-obsidian-type-options.md), extending the [version 1 destination evidence](../../brz-to-obsidian/research/obsidian-representation.md). All external sources below are first-party Obsidian documentation, fetched successfully on this date. No native application trial, community plugin installation or archive upload was performed.

**Finding:** native Obsidian provides ways to store type assignments, navigate to definition notes and display shared appearance. The documented mechanisms do not establish a Brain-style class system or a general rule that a linked note supplies another note's properties, icon or override precedence. A conversion can preserve source facts and add a specified visual adaptation; those are separate outcomes. Candidate mappings remain provisional until the source inventory establishes definitions, assignment cardinality and appearance semantics.

Here, **thought type** means the source concept described by the user. It remains distinct from source tags, parent/child relationships, attachment `Type` fields and Obsidian property/formula data types. Names in examples are synthetic and do not prescribe the output schema.

## Native mechanisms and their consequences

| Mechanism | Membership and discovery | Appearance and inherited behavior |
| --- | --- | --- |
| Linked property, e.g. `brain_types: ["[[Types/example]]"]` | Text/list properties accept quoted wikilinks; lists support several values. Property names have one data type throughout the vault. Unique keys, flat values and the absence of Markdown rendering constrain the representation. [Properties](https://obsidian.md/help/properties). | Stores assignments; a link alone does not specify copied defaults, validation or source override rules (**inference**). List capability is not evidence that TheBrain permits multiple types. |
| Ordinary definition note | A real Markdown note can retain a definition's identity, content and appearance facts. Internal links can target notes that do not yet exist; folder-qualified wikilinks use vault-root paths. [Internal links](https://obsidian.md/help/links), [Data storage](https://obsidian.md/help/data-storage). | A definition note is a chosen convention. Storing a color or image reference is distinct from displaying it on members (**inference**). |
| Vault tags and Search | Tags are searchable keywords, including slash-separated hierarchies; they are case-insensitive and cannot contain spaces. Prefix searches include nested tags. Search supports `[property]`, `[property:value]` and embedded `query` blocks. [Tags](https://obsidian.md/help/tags), [Search](https://obsidian.md/help/plugins/search). | A type namespace could be an additional discovery projection (**candidate**). Its hierarchy does not establish source inheritance; distinguish it from converted source tags and retain a mapping for transformed names. |
| Backlinks and Graph | Backlinks list incoming internal links. Graph lines represent links; arrows indicate direction. Graph can include uncreated targets, controlled by **Existing files only**, and tags via a separate toggle. [Backlinks](https://obsidian.md/help/plugins/backlinks), [Graph view](https://obsidian.md/help/plugins/graph). | Search-based Graph groups color nodes. Documented nodes are circles; these controls do not document custom per-node icons or inherited styling. Type links add connections with the same native edge vocabulary as ordinary links (**inference**). |
| Bases | Core Bases views filter, sort and edit files/properties; definitions are `.base` files or embedded code blocks. [Bases](https://obsidian.md/help/bases). Wikilinks become Link objects: equality compares targets; list `contains` can test membership against `this`. `file.links` includes frontmatter. [Bases syntax](https://obsidian.md/help/bases/syntax). | Formula values are calculated for Bases views. Links have `asFile()`; file objects expose `properties`. `image()` renders an image and `icon()` accepts supported Lucide names. [Formulas](https://obsidian.md/help/formulas), [Functions](https://obsidian.md/help/bases/functions). **Candidate:** calculate an appearance from a linked definition inside a view; this does not establish vault-wide inheritance. |
| Templates and note embeds | Templates insert predefined text into the active note; template properties are added/merged when inserted. [Templates](https://obsidian.md/help/plugins/templates), [Properties](https://obsidian.md/help/properties). | Template defaults are inserted content, not a documented continuing relationship (**inference**). Note/heading/block embeds display source content and stay updated when it changes. An embedded definition section could share readable information or an image; it does not assign member metadata. [Embed files](https://obsidian.md/help/embeds). |
| CSS snippets and `cssclasses` | Notes can carry one or several CSS class names. Snippets live in the vault configuration folder, must be enabled, and update when saved. [CSS snippets](https://obsidian.md/help/snippets). | A shared class can style member notes centrally. Mapping type assignments to classes, choosing selectors and handling overrides are adaptation rules; the documented mechanism does not bind arbitrary linked definition properties to CSS (**inference**). |

Bases Cards can use a local attachment link, external URL or hex color as a cover image property. This offers an image/color index, rather than evidence of a global note icon. Views can group by one property; the documentation lists Table/Cards from Obsidian 1.9, with some other layouts requiring later or early-access versions. Record the actual installed version before promising a layout. [Cards view](https://obsidian.md/help/bases/views/cards), [Views](https://obsidian.md/help/bases/views).

## Boundaries that affect the conversion

- **Assignment-specific discovery:** a backlinks pane or Bases `file.hasLink()` includes links of other meanings. A reference to a definition in prose or ordinary hierarchy is not necessarily membership. A property-specific Bases filter such as `brain_types.contains(this)` in an embedded definition note is a documented-syntax candidate; exact property Search queries and rendering still need a trial. [Backlinks](https://obsidian.md/help/plugins/backlinks), [Bases syntax](https://obsidian.md/help/bases/syntax), [Functions](https://obsidian.md/help/bases/functions).
- **Uncreated targets:** Graph visibility is configurable; visibility does not create a definition file. `asFile()` requires a valid local file. **Inference:** reading a definition's properties requires its file, and storing membership as note properties requires a member file. The earlier empty-thought policy therefore needs an explicit decision for definitions and members. [Graph view](https://obsidian.md/help/plugins/graph), [Functions](https://obsidian.md/help/bases/functions).
- **Overrides and overlapping assignments:** the referenced native documentation supplies no source-specific precedence rule. Decide whether to preserve declared source values, show an effective appearance, or offer both. A formula fallback, generated CSS mapping or overlapping Graph groups must not silently decide that question. Group-overlap precedence and linked-definition refresh behavior remain trial questions.
- **Portable presentation:** vault-specific settings live in `.obsidian` by default; the configuration folder can be overridden. A copied vault must include any required local media, `.base` files and enabled CSS configuration, and use vault-local paths. The precise Graph configuration serialization is not established by the referenced docs. [Data storage](https://obsidian.md/help/data-storage), [Configuration folder](https://obsidian.md/help/configuration-folder), [CSS snippets](https://obsidian.md/help/snippets). Copying settings is a candidate requiring verification, not a verified deployment recipe.

## Remote video attachments

The source scout supplied an aggregate observation: four URL attachment records contain `VideoHtml` iframe strings. This is an archive fact to reconcile with the completed inventory, not a guarantee that any iframe will play. No private URLs were accessed or reproduced here.

Native Obsidian documents `<iframe src="…"></iframe>` web embeds, warns that some sites disallow embedding or require a special embed URL, and supports YouTube embeds using external-image Markdown syntax. Preserve a usable external link alongside any chosen adaptation; embedding a remote resource does not archive its bytes or establish offline playback (**inference**). [Embed web pages](https://obsidian.md/help/embed-web-pages).

HTML is sanitized; HTML blocks must be self-contained without blank lines, and Markdown inside HTML elements is not rendered. Consequently, retaining the source iframe string does not by itself prove equivalent rendering or preservation of all attributes. [HTML content](https://obsidian.md/help/html). If video bytes actually exist locally, supported video extensions include `.mkv`, `.mov`, `.mp4`, `.ogv` and `.webm`; native preview depends on device codecs. Local embeds are a separate route, not a reason to fetch URL attachments. [Accepted file formats](https://obsidian.md/help/file-formats), [Embed files](https://obsidian.md/help/embeds).

## Candidate choices and required native trials

Choices can be combined; none is selected here:

1. **Definition notes plus linked membership:** preserve semantic identity and source facts, with readable navigation. Decide materialization and whether body links duplicate properties.
2. **Add discovery views:** optional type-tag projection, property Search/indexes and/or Bases. Decide how type membership stays distinct from other classifications and connections.
3. **Add appearance adaptations:** Graph color groups, shared note CSS, embedded definition sections, and/or Bases images/icons. Specify which surfaces matter and whether their values are snapshots or computed views. A community extension would be a separate dependency and research choice if accepted behavior exceeds the verified native mechanisms; none is proposed or required by this report.

Use a disposable synthetic vault, record Obsidian version, theme, core plugins and settings, and keep all community plugins disabled:

- Compare scalar/list property links with body links; include zero, one and two assignments, duplicate display names, a renamed definition, an uncreated definition, and a type-only member. Check the property editor, exact membership Search, Backlinks and Graph with **Existing files only** both ways. Include a prose link to the definition as a false-positive control.
- Trial a definition-embedded membership Base and linked-property appearance lookup. Change the definition, reload/reopen the view, exercise absent targets/values and compare explicit overrides. Check list grouping, image/hex covers and icon rendering; verify whether formulas affect anything outside the Base before claiming they do.
- Change a shared CSS rule, test multiple classes/overlapping Graph groups, and inspect Reading view, Live Preview, file navigation and Graph separately. Test an embedded definition section and a later template edit. Record each surface's actual behavior and precedence.
- Copy the vault to another root and reopen it, with and without its configuration folder. Verify paths, media, classes, enabled snippets, Bases and Graph colors. Document settings needed to reproduce the accepted presentation.
- For public synthetic video URLs, test iframe and documented YouTube syntax, source attributes and fallback links, offline operation, and a site that refuses embedding. Test local video only with a known fixture. Record adaptation and unavailable playback distinctly.

These trials establish destination behavior; controlled TheBrain evidence must establish the source's inheritance and override rules before the human chooses the version 2 contract.
