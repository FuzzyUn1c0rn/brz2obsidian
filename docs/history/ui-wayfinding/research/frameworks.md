# Desktop UI framework comparison

Research for [issue #86](https://github.com/FuzzyUn1c0rn/brz2obsidian/issues/86), accessed 2026-10-08. This report informs a later human stack decision; it does not select or implement a stack.

## Scope and conclusion

The accepted destination is a Windows-first, launchable, local/offline application requiring no user-installed Python or Git. It handles one archive at a time, with a guided archive-selection → inspection → findings → destination → conversion flow and independent Inspect and Check vault modes. Existing Python APIs and versioned JSON CLI results are possible boundaries. Detailed Python packager choices belong to [issue #87](https://github.com/FuzzyUn1c0rn/brz2obsidian/issues/87).

**Reasoned shortlist: PySide6 with Qt Widgets and Electron.** PySide6 keeps the product in Python and supplies mature desktop forms and documented accessibility integration. Electron is the strongest HTML/CSS alternative if the maintainer prefers web UI development and accepts a bundled browser and a separate Python helper. **Tauri is a credible conditional third candidate**, especially for someone comfortable maintaining Rust and a web frontend. **Tkinter/ttk and pywebview remain possible smaller alternatives**, with accessibility and Windows dependency verification respectively deserving more weight than the apparent simplicity of a hello-world example. These are project-fit judgments, not measured performance or maintenance rankings.

All five can represent the three modes and use file/directory dialogs. None requires an account or cloud conversion. Offline operation is an application/distribution choice: ship UI assets locally and bundle the converter/runtime. A packaged proof is still required; reading framework docs does not prove this repository's delivered executable.

## Comparison

| Candidate | Forms, diagnostics and native pickers | Responsive converter integration | Maintenance and Windows distribution implications |
| --- | --- | --- | --- |
| **PySide6 / Qt Widgets** | Standard widgets cover labelled path fields, forms, tabs, tables and selectable diagnostic text. `QFileDialog.getOpenFileName` and `getExistingDirectory` use Windows native dialogs. Qt documents keyboard navigation, system fonts/palette and platform accessibility APIs. [Qt accessibility](https://doc.qt.io/qt-6/accessible.html), [QFileDialog](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QFileDialog.html) | Direct public Python calls in a worker, with results marshalled back to the GUI; or a packaged JSON CLI helper via asynchronous `QProcess`, which provides output/error/finished signals. Keep work and blocking waits off the GUI thread. [QThread](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QThread.html), [QProcess](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QProcess.html) | One main application language, plus Qt's signal/slot and lifecycle concepts. Bundle Python, required Qt DLLs/plugins and runtime dependencies; no WebView2 requirement for a Widgets-only UI. Qt's deployment documentation covers plugin/runtime collection. This is likely the least cross-language integration for this converter, but Qt licensing/distribution needs deliberate treatment. [Windows deployment](https://doc.qt.io/qt-6/windows-deployment.html) |
| **Electron** | HTML/CSS forms and diagnostics; native main-process `dialog.showOpenDialog` supports separate file and directory pickers. Accessibility uses Chromium's tree and standard web semantics, with automatic assistive-technology detection. [Dialog](https://www.electronjs.org/docs/latest/api/dialog), [Accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility) | Renderer → narrow preload/IPC API → main-process supervisor → bundled Python CLI executable. Node's asynchronous `spawn` supports argument arrays, pipes and `windowsHide`. Electron `utilityProcess` runs Node modules; it is not a Python interpreter and should not be described as Python execution support. [Node child processes](https://nodejs.org/api/child_process.html), [utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process) | Maintain JS/TS + HTML/CSS + Python and a process/result boundary. Ships Chromium/Node as part of Electron, reducing dependency on installed browser versions but increasing shipped runtime footprint (unmeasured here). Follow context isolation/sandboxing and expose only required operations. Electron supports its latest three stable major versions, so budget ongoing upgrades. [Process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Security](https://www.electronjs.org/docs/latest/tutorial/security), [Release support](https://www.electronjs.org/docs/latest/tutorial/electron-timelines) |
| **Tauri 2** | Web forms/diagnostics in the OS webview; official dialog plugin provides native file and folder pickers on Windows, including single selection. Accessibility of the completed frontend still needs testing; no claim that framework selection makes forms accessible automatically. [Dialog plugin](https://v2.tauri.app/plugin/dialog/) | Official external-binary/sidecar support explicitly covers avoiding user-installed Python. Bundle a frozen CLI helper, use argument arrays and scoped command permissions, and receive stdout/termination events. It does not import Python directly into Rust. [Sidecars](https://v2.tauri.app/develop/sidecar/) | Adds Rust/native build tooling as well as the web frontend and Python helper. Development prerequisites include MSVC build tools/Rust/WebView2; these are developer requirements, not a demand that users install compilers. Windows UI requires WebView2. Official installers support offline and fixed runtime modes, while the default downloaded bootstrapper requires internet. [Prerequisites](https://v2.tauri.app/start/prerequisites/), [Windows installer](https://v2.tauri.app/distribute/windows-installer/) |
| **Tkinter / ttk** | Python standard-library binding with themed widgets, basic forms, text and tree views. `askopenfilename` and `askdirectory` provide native dialogs. Adequate for a deliberately plain utility, but more manual layout/diagnostic presentation work is a project-fit inference. [ttk](https://docs.python.org/3.14/library/tkinter.ttk.html), [Dialogs](https://docs.python.org/3.14/library/dialog.html) | Direct Python worker execution or subprocess helper. Tk's event loop must stay responsive; documentation explicitly directs long computations out of event handlers. Deliver updates on the GUI event loop (for example, queue polling via timers); do not have workers own widgets. [Tkinter threading](https://docs.python.org/3.14/library/tkinter.html#threading-model) | Smallest new framework surface for an existing Python project; deployment must still collect Tcl/Tk libraries/data alongside Python. Python's official binary distribution bundles Tk 8.6. New Tk 9.1 accessibility API documentation is not evidence that stock Python/Tk 8.6 meets the desired Windows screen-reader behavior. Treat this as a candidate-specific proof requirement. [Python Tk version](https://docs.python.org/3.14/library/tkinter.html), [Tk 9.1 accessible API](https://www.tcl-lang.org/man/tcl9.1/TkCmd/accessible.html) |
| **pywebview** | HTML/CSS frontend with a Python host and API bridge. `create_file_dialog` exposes file and folder selection. Forms/readable results are feasible, but accessibility must be tested on the actual Windows webview. [API](https://pywebview.flowrl.com/api/) | JS calls to exposed Python methods return promises; methods execute on separate threads and are explicitly not thread-safe. Host GUI loop stays on the main thread. Serialize jobs despite repeated clicks; direct converter calls or a subprocess helper are both possible. [JS–Python bridge](https://pywebview.flowrl.com/guide/interdomain.html), [FAQ](https://pywebview.flowrl.com/guide/faq) | Avoids a Rust shell or bundled Node runtime, while retaining two frontend/backend languages. Windows Edge backend adds pythonnet, .NET Framework and WebView2. Official engine docs still describe fallback to deprecated MSHTML; explicitly require `edgechromium` and provision its runtime rather than silently presenting an obsolete browser. [Installation](https://pywebview.flowrl.com/guide/installation.html), [Web engine](https://pywebview.flowrl.com/guide/web_engine.html) |

## Compatibility confidence

- **PySide6:** Qt's published compatibility matrix lists Python 3.14 support from the 6.10 series, and for 6.11/6.12; it notes free-threaded Python is not fully supported. Use ordinary CPython 3.14 and pin an available supported release. The matrix is maintained on Qt's official wiki, so a clean Windows build remains the final test. [Qt Python matrix](https://wiki.qt.io/Qt_for_Python#Python_compatibility_matrix)
- **Tkinter:** Python 3.14 directly documents the binding. This establishes language integration, not a guarantee of the selected packager's Tcl/Tk collection or screen-reader behavior. [Python 3.14 Tkinter](https://docs.python.org/3.14/library/tkinter.html)
- **Electron/Tauri:** the shell is independent of Python version because the proposed boundary is a separately bundled executable. Their documented process/sidecar capabilities do not verify that the converter's Python 3.14 build runs correctly; that is #87's boundary.
- **pywebview:** its Windows dependency pythonnet now has an official 3.2.0 distribution released September 29, 2026, with CPython 3.14 in the wheel tags/classifiers. That removes the historical broad claim that pythonnet lacks 3.14 support. It does **not** establish end-to-end frozen pywebview/3.14/WebView2 compatibility. [pythonnet release metadata](https://pypi.org/project/pythonnet/)
- **Windows floor/architecture:** “Windows first” is not yet an exact supported OS/build/CPU matrix. Electron ended Windows 7/8/8.1 support after Electron 22. Qt 6's supported-platform page must be checked for the pinned release. Runtime requirements across Python, Qt/WebView2 and a selected packager must be intersected before promising a minimum Windows version. [Electron OS change](https://www.electronjs.org/blog/windows-7-to-8-1-deprecation-notice), [Qt supported platforms](https://doc.qt.io/qtforpython-6/overviews/qtdoc-supported-platforms.html)

## License and redistribution considerations

These summarize first-party license text and distribution guidance; final obligations depend on the exact bundled versions, modules and release format.

| Component | Published license / practical distribution consideration |
| --- | --- |
| Electron | MIT text requires retaining copyright/permission notice. Chromium, Node and bundled dependencies have additional notices; ship the applicable notices from the actual release. [Electron license](https://raw.githubusercontent.com/electron/electron/main/LICENSE) |
| Tauri | Project SPDX declares Apache-2.0 and MIT. Retain the chosen license and applicable notices, and audit bundled plugins/dependencies and the Python helper separately. [Tauri SPDX](https://raw.githubusercontent.com/tauri-apps/tauri/dev/LICENSE.spdx) |
| PySide6 / Qt | Qt for Python publishes LGPLv3/GPLv3/commercial licensing. For an LGPL route, Qt's guidance calls for notices/license text, source availability for the library and modifications, and the user's ability to replace/relink the library; its guidance recommends dynamic linking. Check module licenses and avoid assuming a single-file frozen executable automatically satisfies replacement requirements. Commercial licensing is an alternative. [Qt for Python](https://doc.qt.io/qtforpython-6/), [Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations) |
| Tkinter / Tcl/Tk | Python is PSF-licensed with retained component notices; Tcl/Tk's permissive terms require retaining its copyright/license notice. Include the licenses for the precise Python/Tcl/Tk binaries shipped. [Python license](https://docs.python.org/3.14/license.html), [Tcl/Tk license](https://www.tcl-lang.org/software/tcltk/license.html) |
| pywebview | BSD 3-Clause requires retaining notices/disclaimer and prohibits unapproved endorsement. pythonnet is MIT; WebView2/.NET and other binary dependencies require their own distribution review. [pywebview license](https://raw.githubusercontent.com/r0x0r/pywebview/master/LICENSE), [pythonnet metadata](https://pypi.org/project/pythonnet/) |

Offline **use** and offline **installation** are separate promises. If installation must also work with no network on a clean Windows system, Tauri/pywebview need an offline WebView2 provisioning plan. Tauri's documentation provides offline-installer and fixed-runtime options; its illustrative size numbers should not be treated as measured current installer sizes. A fixed runtime also transfers update responsibility to the app. #87 owns the detailed packaging/deployment recommendation. [Tauri runtime options](https://v2.tauri.app/distribute/windows-installer/)

## Proposed decision and proof boundary

Ask the human to choose the preferred maintenance direction after viewing a small workflow mockup: **Python desktop widgets** (PySide6) or **web UI** (Electron, with Tauri conditional on willingness to maintain Rust). Do not select by framework popularity or promise a polished UI based on the toolkit alone. Tkinter is reasonable only if its plainer presentation and measured accessibility are acceptable; pywebview is reasonable if its simpler Python host offsets the extra Windows dependency chain.

Before committing to the chosen candidate, one bounded technical proof should:

1. Package a minimal window and converter boundary, launch on the agreed clean Windows target without Python/Git and with networking disabled. For a webview candidate, verify the chosen runtime provisioning path explicitly.
2. Use a synthetic archive and a disposable output directory; run Inspect, Convert and Check vault while moving/resizing the window. Verify Unicode/spaces in paths, picker cancellation, unreadable archive, existing destination, malformed helper output and crash handling. Keep the window responsive and allow copying readable findings.
3. Verify keyboard-only navigation, associated labels, focus after errors/step transitions, system scaling/high contrast, and a representative Windows screen-reader pass. For Tkinter, specifically establish the behavior of the exact bundled Tk version; for web UIs, use semantic controls and announce status changes without flooding the reader.
4. Define lifecycle behavior while conversion runs. Background execution does not prove safe cancellation: if the converter has no cooperative cancel/rollback contract, do not expose a Cancel button that merely kills a process and implies cleanup. Inspect process exit and partial-output policy separately.

These checks are a proposed later spike, not performed research. No framework was installed, UI was built, private archive was opened, native app was inspected, or source file was changed for this report. No executable size, speed, accessibility or end-to-end packaging claim is measured here.
